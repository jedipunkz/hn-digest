random-bench / Benchmarks are Astrology for LLMs
Benchmarks are a hot topic lately. Every other week, some new model has achieved some incredible number on a benchmark I've never seen before. I, personally, am tired of the benchflation pioneered by certain reckless frontier AI companies. Although they're often marketing nonsense, leakage is probably real, and “rogue” agent cheating is more common than ever, there's a certain mystical appeal to benchmarks, and they do generally signal improvement, give or take. While they may not be perfect (or, in some cases, meaningful in real-world contexts at all), you can learn quite a bit about models from their performances on even arbitrary tasks. To quote an astrology article I read in 2020 that shaped a large part of my stubborn adolescent pragmatist epistemology:
it doesn't matter if astrology is real; it matters if it's useful.
random-bench is a (very much vibecoded) benchmark of frontier LLMs to evaluate their ability to generate random numbers. For this I use mostly basic Shannon entropy and, to the extent it's necessary to show just how bad models are at this task, the NIST random bit generation test suite (packaged in this python module ).
The process is as simple as it sounds; I send a prompt to each model asking it to select a number between 0 and 255 (one byte), do that 255 times, then concatenate the returned byte into a 2048-bit-long sequence. And then I repeat that 54 times per model (NIST minimum - don't ask). A bunch of magic happens and we're finally left with a score of random-ness.
Let's dig into a few of the results:
Here you'll see the Shannon entropy of each model in bits per byte, with the control CSPRNG (cryptographically secure pseudo-random number generator, python default) at just about the max score of 8. You'll kind of notice a pattern here; more modern models tend lower on the list, which makes sense, because I've certainly felt like outputs have gotten more regular as models evolve. This seems to plot well.
Another interesting angle is the share of responses per number:
This feels ridiculous, right? 60.1% of all responses across different providers are 173?
Even further, you'll see that 8 of the models practically chose nothing but 173 (I promise, I checked, the responses aren't cached or anything). All of these are OpenAI models, but 4 Anthropic models fail to get past the first 2 most common responses, so it's not isolated to a single provider.
(For the sake of illustration, only LLM responses are considered for the “most-chosen” ranking; I thought this showed the split between conversational LLMs and BERT models nicely)
If Anthropic and OpenAI are “over-correcting” by choosing numbers that, at face value, look “random,” then BERT is “under-correcting.” It prefers numbers that are most often used in written language - that is, numbers like 0, 1, 2, and 3. In fact, 76% of bert-base-uncased and 53.4% of ModernBERT-large answers were between 0 and 10. I had a hunch that this was because of BERT's lack of conversational post-training that the frontier LLMs come packaged with - one is trying to “fill in the gaps” with numbers that make sense based on all the writing it's seen, and the other is trying to follow an instruction and choose a number that, to a user, looks “more random.”
And I was right, at least in my outcome hypothesis. The instructional model is still not perfect, but it does do much better over this sample. ModernBERT-large-instruct still seems to have a bit of a leftover inclination towards the single digits, but it's definitely avoiding the 173/137 trap. My guess for this gap between BERT and frontier is that RLHF (reinforcement learning from human feedback) introduces human randomness biases (humans think 173 and 137 look “very random,” so those numbers end up being over-represented in the LLM's knowledge of “randomness” after human feedback).
Another fun way to show this is the per-bit bias, or the average value of any given bit. It seems like when generating numbers, LLMs tend to follow a pretty human-like pattern: they alternate in predictable ways . The non-instruct BERT models, on the other hand, tend to be 0s up until the very last few bits, which aligns with the 0-10 range we've observed. And the instruct model, while less biased, still retains this tendency - albeit less pronounced.
And to cap it all off before you start to think any of these models are actually good at this, here's my proof that all models really do suck as PRNGs and it's not a strictly practical benchmark. Notice how all the models' NIST scores are low, and don't follow the patterns we've been seeing as far as which models are best? NIST measures the actual attack vectors a malicious actor might exploit - so if you've been thinking about using the 800MB ModernBERT-large-instruct model weights for your cryptographic PRNG: well, you're better off not.

I thought about said video for the first time in a while this past week. Considering I haven't yet found a full-time job, I've got a lot of time on my hands - enough time, that is, for the sort of hijinks that tom7's made himself known for. Being unoriginal, I came up with my very worst project to date: turtlebyte.
Turtlebyte is a virtual hard drive written and read by python's very own turtle. If you don't remember turtle, you probably didn't take a middle school programming class; for short, it's a drawing module most often associated with complete beginners to coding in general. It's slow, it's simple, and it makes a terrible hard drive - but it makes one nonetheless.
Before I get started, all my source code is here . It's actually uploaded to PYPI, so you can install it and test it out with pip install turtlebyte --upgrade , should you feel so inclined.
Some important notes: I didn't want to cheat and use a bunch of teleports - all of the writes and reads are continuous once they've started. This means that, should you turn the animation on, it's actually a pretty smooth watch - albeit a slow one. Programming with turtle is as simple as turtle.fd(10) to move the cursor forward 10 units and turtle.rt(90) to turn right by 90 degrees. I quickly decided on a 4x2 arrangement for the bytes, thinking that that would minimize turns if I can write across a row, turn twice, then write the second row from that position.
And so the clear starting point is a nibble - 4 bits, that is. I wrote a helper function that, at the current position of the turtle, receives a length-4 array with boolean values for the bits, then deposits dots along a line for each True value in the array. So far, so good. Simply turn right, go forward, and turn right again to write the second row and last nibble of the byte.
At this point, I had a method to write a byte at the current position (and read a byte, by a similar process that actually ended up being a headache because of turtle's attempt to be as beginner-friendly and feature-sparse as possible). That isn't quite enough to mimic a hard drive, so I began work on write_bytes , a method that takes a byte address and an array of bytes as input, then writes exactly what and where you'd expect it to. The read_bytes function acts similarly with an address and a number of bytes to read. Just split longer byte arrays into blocks and all should be well.
After many bugfixes, I had a working product. Here's turtlebyte writing every byte from 0x00 to 0xFF , sped up 8x because turtle with animations on is super slow
Then I toggled animations off and tested real data by turning a smaller pdf document (which happened to be my college transcript) into one of these QR-code looking things:
And for good measure, I ran turtlebyte again on the .png that a screenshot of the previous image produced.
This is something around 70kb of data and took about 15 minutes. For a little more context, the program writes bytes from top to bottom, then starts at the next column to the right. Blocks are 16x32 bytes to make that square shape (remember - bytes are twice as long as tall), and blocks are also written top-to-bottom then left-to-right.
I then moved on to something more dynamic. I present to you, running at a whopping 3 frames per second (sped up 4x for this GIF), turtlebyte pong:
The source code is undocumented, platform-specific, sloppy, and probably not worth the effort of making work on your machine. Succinctly: turtlebyte is running an instance of tkinter (running concurrent turtle windows took MAJOR refactoring and so much headache digging through docs and source code), the game board is running a turtle instance, and each object on the game board inherits from a C-like ObjectStruct class that stores all relevant memory in the turtlebyte instance. I tried to be as loyal to the spirit of the project as I could, so this is the only place that position data exists (meaning, nowhere in the code of gameboard) and each frame is basically a complete refresh.
Anyways, that's what I've been up to for the last week. Don't be afraid to try the module yourself (but please, not the pong). Maybe I'll bake the struct-like class in for the sake of intuition, but probably not. Until next time!
