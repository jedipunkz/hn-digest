Home
Coding agents are getting remarkably good at writing LLM infrastructure, from GPU kernels and schedulers to custom serving engines. Suppose an AI agent is strong enough to build a fast inference engine from scratch; in this second half of the problem, the bottleneck shifts from capability to verification : how do we know the engine it wrote is actually correct? Passing latency and throughput benchmarks still leaves rare concurrency bugs hidden. As a single engineer begins orchestrating 100, 1,000, or even 10,000 coding agents in parallel, human code review hits a hard cognitive wall. Having agents review other agents does not solve this either; as pstack author Lauren Tan noted , adversarial reviews are mostly a waste of tokens, and it is far better to spend those tokens on empirical and formal verification.
In this post, we introduce vstack , a 5-stage formal verification workflow for coding agents, and veriserve , a prototype verifiable LLM serving engine with PD disaggregation built around a formally verified KV-page lifecycle design model. Applying vstack to production Prefill-Decode serving uncovered three classes of real RDMA and cache concurrency bugs across SGLang and vLLM, resulting in 6 proposed upstream pull requests . Meanwhile, veriserve backs its PdLedger design model with a 226-module, 516,973-obligation TLAPS safety proof while adding only 0.18% mean p50 TPOT overhead on NVIDIA GB200. We believe verifiable serving defines the second half of LLM infra as autonomous coding agents write the deepest layers of production systems.
Why We Need Verifiable Serving #
Why is verifying an LLM serving engine so hard in the first place? Over the past three years, inference engines like vLLM and SGLang have evolved from single-node executors into asynchronous distributed systems, layering paged KV memory , shared prefix caching , and disaggregated prefill-decode RDMA transfers over the same pool of physical GPU KV pages. When a request times out or aborts, its cleanup now races across RDMA network cards, CPU cache trees, and GPU attention kernels simultaneously. Because GPUDirect RDMA writes directly into GPU memory without involving the target CPU, a lifecycle mismatch often does not crash the server, but returns HTTP 200 OK while silently mixing one user’s KV cache into another user’s response. Recent LMSYS and Cloudflare disclosures highlight this risk in production, documenting both cross-node RDMA abort races and a rejected-request KV handoff bug that exposed data across 155 user responses .
Worse yet, catching these silent concurrency bugs on real hardware is slow and prohibitively expensive . Standard CI unit tests run on a single machine and only cover known paths, while subtle distributed races under rare asynchronous interleavings rarely surface in CI. Reproducing an RDMA lifecycle race requires multi-GPU RDMA hardware like H100 or GB200, separate prefill and decode instances, and tight cross-worker timing. Flushing them out with long stress tests on GPU clusters burns scarce compute and still cannot guarantee that all race conditions are gone.
To catch these deep concurrency bugs without burning GPU hours, we turn to formal verification : modeling the system as a state machine and combining TLA+ model checking with Z3 and TLAPS theorem provers to exhaustively explore millions of asynchronous schedules and prove safety invariants on CPUs. In the past, formal verification was impractical for AI infrastructure because engines like vLLM and SGLang merge new pull requests continuously, while manually writing and updating formal specifications and proofs takes months of human effort. Today, coding agents give us a practical way to bridge this gap. Because LLMs can read large systems codebases and generate thousands of lines of formal specifications and proofs far faster than manual proof engineering, we can guide coding agents to specify, model-check, and prove critical subsystems, making verifiable serving practical in fast-moving open-source projects.
How We Verify: Formal Verification with vstack #
Turning agent-driven formal verification into a reliable workflow requires solving two immediate challenges. First, the hardest part of formal verification is not running the solver, but writing an accurate Specification : a requirement the software must never violate under any asynchronous schedule. Thanks to open-source vLLM and SGLang , we do not invent these requirements in a vacuum, but ground them directly in real user issues, bug-fix PRs, and GPU kernel preconditions.
Second, even with a clear specification, simply asking a coding agent to write a formal model and prove it rarely works out of the box. When a model checker reports a race condition, a naive coding agent will often reward-hack the verifier : instead of surfacing the real bug, it weakens the invariant, deletes the timeout branch from the model, or adds an unrealistic ASSUME statement so the checker returns 0 errors .
To prevent reward hacking and make agent-driven verification reliable, we built vstack , an open-source plugin for Claude Code and Cursor that enforces a 5-stage verification workflow :
Specification : Encode software requirements as formal safety invariants and pin the specification files by hash so unapproved edits to the proof goal are detected and rejected.
Abstraction : Build TLA+ and Z3 models where every state transition maps to an exact file:line@commit in the production codebase, splitting non-atomic cross-thread and cross-node operations into separate steps.
Validation : Before trusting any proof, verify model fidelity against real code: the historical buggy code must fail on the model, the patched code must pass, removing a guard from the fix must fail again under nonredundant mutation checks, and recorded execution traces must replay cleanly through the model.
Verification : Run TLC breadth-first search to find the shortest counterexample trace within the bounded model, then use Apalache , Z3 , and TLAPS to prove that the modeled state machine and GPU KV-buffer address arithmetic hold under our explicit configuration assumptions.
Continuous Checking : Re-run the specification suite on new pull requests on CPUs, and mirror the proven preconditions as lightweight runtime checks in the engine.
Case Study: Formally Verifying Prefill-Decode Disaggregated Serving #
As a prototype, we applied vstack to Prefill-Decode Disaggregated Serving , where a Prefill node computes the prompt’s KV cache and transfers it over one-sided RDMA to a Decode node that shares cached prefixes and runs the Decode attention kernel, as shown in Figure 2 . For this core KV page subsystem, we define four specifications :
Isolation : In-flight RDMA transfers or late control messages from an old request must never read or overwrite a new request’s memory or state.
Integrity : Every KV page read by the Decode kernel or published into the global prefix cache must contain complete, uncorrupted data from the intended request generation.
Finality : Every active request and draining memory page must reach a terminal state in finite steps rather than hanging forever.
Conservation : Every physical page is strictly accounted for: a page exposed to in-flight RDMA returns to FREE only after hardware stop evidence arrives, or else stays permanently isolated in QUARANTINED accounting.
Uncovering Real Concurrency Issues in SGLang and vLLM #
Checking the production Prefill-Decode implementations of SGLang and vLLM against these four specifications on CPUs uncovered three classes of concurrency issues , for which we reproduced selected RDMA failure paths on NVIDIA GB200 and control-plane deadlocks on CPUs, and submitted 6 proposed upstream pull requests :
Reclaiming Transfer Slots or KV Blocks While RDMA Is Still In Flight: When a request aborts or times out, one-sided RDMA transfers already queued on the NIC cannot be canceled in hardware on the studied transport paths; yet both engines allowed new requests to reuse the same transfer identity or reallocate the expired GPU page before the hardware transfer stopped, violating Isolation . On GB200, we reproduced this race in both SGLang and vLLM, where late RDMA accesses silently read or overwrote another request’s KV cache under HTTP 200 OK . We proposed upstream fixes in SGLang #48883 , #48889 , #48960 , #48979 , and #48982 , alongside a related vLLM pull-validation PR #62065 by @vadiklyutiy .
Publishing Race-Corrupted KV Pages into the Global Prefix Cache: When an RDMA transfer finishes, the Decode node can insert the received KV pages into the global prefix cache without checking whether the page’s lifecycle generation was invalidated mid-flight, violating Integrity . In our vLLM GB200 experiment, race-corrupted KV pages entered the prefix cache and corrupted a subsequent request that reused the cached prefix. This motivates tracking versioned page ownership consistently across the RDMA transfer and prefix-cache boundary.
Unrenewed Transfer Leases and Hung Decode Requests: When a remote transfer stalls or an abort notification is dropped, unrenewed leases and missing watchdogs leave Decode requests waiting indefinitely while holding their allocated GPU pages, violating Finality and Conservation . We reproduced stalled RDMA leases on GB200 and scheduler capacity deadlocks in CPU control-plane replay, and proposed an upstream lease-renewal and receive-timeout fix in vLLM #66443 .
Why Local Timeouts Fail: The deepest lifecycle failures above share a fundamental root cause: using local CPU timeouts or error codes to guess when asynchronous hardware RDMA has finished . Using TLAPS and Z3 , we formally proved that under unbounded asynchronous delay and indistinguishable local histories without trustworthy stop or revocation evidence, any local-only page reclamation policy cannot guarantee both Isolation if it reclaims the page early and eventual page reclamation under page-level Finality if it holds the page forever.
Building veriserve : A Verifiable LLM Serving Engine #
Because no local-only timeout policy can escape this trade-off, current engines like SGLang and vLLM remain vulnerable when their RDMA connector, prefix cache, and decode scheduler maintain separate local counters over raw page_id integers and guess when hardware RDMA is done. To fix this by design, we built veriserve , a verifiable LLM serving engine with PD disaggregation on mini-sglang and Mooncake GPUDirect RDMA centered on a single capability state machine, PdLedger , which tracks every physical page via a versioned ticket (page, gen) across six explicit implementation states: FREE , PRIVATE , SHARED , DRAINING , QUARANTINED , and DUP , with Figure 3 illustrating the four states on the RDMA timeout and cancellation paths.
Our key design delta is using DRAINING and QUARANTINED to decouple request cancellation from hardware DMA completion , resolving the request-hang-versus-corruption trade-off:
Release with Stop Evidence → FREE : Releasing a private page with outstanding RDMA or kernel accesses moves it to DRAINING first. Once hardware completion or peer acknowledgement confirms all tracked accesses have stopped, PdLedger returns the page to FREE , while each new request incarnation receives a fresh generation identifier gen , preserving Conservation .
